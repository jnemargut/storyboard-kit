The Storyboard File Format

Technical🚪 One-way doorHigh stakes

A designer writes something loose like "Maya's in line at the coffee shop, order's late, she's annoyed, checks the app." Claude Code or Codex turns that into a file. The editor draws that file as a storyboard, the designer's drag-and-drop tweaks get saved back into it, and the export reads it too. So the file is the contract between three readers: the AI, the editor and the designer. Below is that same coffee-shop panel written four different ways.

Story-First JSON + Schema

coffee-order.storyboard.json 
{
  "panels": [{
    "id": "p3",
    "scene": "coffee-shop/counter",
    "shot": "over-the-shoulder",
    "characters": [{
      "who": "maya", "pose": "holding-phone",
      "mood": "annoyed", "device": "phone"
    }],
    "screen": "./screens/order-status.png",
    "bubbles": [{ "type": "thought",
      "text": "It said 4 minutes. 12 min ago." }],
    "gesture": { "type": "tap", "on": "screen" },
    "layout": { "maya": { "x": 0.42 } } ← only if nudged
  }]
}
AI writes→ storyboard validate ✓→ editor⇄ clean write-back
The file says what's happening (who, where, which shot, which mood), not where each pixel goes. Every word like "over-the-shoulder" or "annoyed" comes from a published vocabulary, so the tool ships a validate command that tells the AI exactly what it got wrong ("'frustated' isn't a mood, did you mean 'frustrated'?"). When a designer drags Maya a bit left in the editor, only a tiny layout override gets written. The story stays readable and the AI can keep rewriting it.

Works well when

  • The AI is the main author. JSON is the format models get wrong least often
  • Editor tweaks and AI rewrites need to live together without clobbering each other
  • You want autocomplete and errors in VS Code for free (JSON Schema)

Watch out for

  • Designers rarely want to hand-edit brackets and quotes
  • No comments allowed, so no "TODO: ask research about this" notes except in a notes field

Readable YAML Spec

coffee-order.storyboard.yaml 
panels:
  - id: p3
    scene: coffee-shop/counter
    shot: over-the-shoulder
    # Maya's the "busy commuter" persona
    characters:
      - who: maya
        pose: holding-phone
        mood: annoyed
        device: phone
    screen: ./screens/order-status.png
    bubbles:
      - thought: "It said 4 minutes. 12 min ago."
    gesture: { tap: screen }
AI writes→ indent errors?→ editor⇄ comments may drop
Same idea as A (a story, not pixels) in a friendlier costume: no brackets, and designers can leave # notes. It's nicer to read and scan in a pull request. The catch is that indentation carries meaning, so one wrong space quietly changes what belongs to what. The editor also has to be very careful when saving tweaks back, or it'll wipe those comments.

Works well when

  • Designers will open the file themselves and edit text directly
  • Teams want inline comments and research notes next to panels

Watch out for

  • LLMs make more syntax slips in YAML than in JSON
  • Round-tripping through an editor loses comments even with specialist libraries
  • Oddities like no being read as false

Markdown Screenplay

coffee-order.storyboard.md 
# Late Latte
Persona: Maya, commuter · Tue 8:14am

---
## Panel 3 · COFFEE SHOP — COUNTER
OVER THE SHOULDER on Maya.

Maya (annoyed) holds her phone.
She [taps] the order screen
![screen](./screens/order-status.png)

> (thought) It said 4 minutes. 12 min ago.

---
## Panel 4 · TIME CARD
Eight minutes later…
AI writes→ custom parser guesses→ editor⇄ where do nudges go?
Reads like a film script. --- separates panels (the way Slidev separates slides), and ALL-CAPS lines set the scene and camera. It's lovely: designers can read the whole journey top to bottom, and it doubles as the narrative that goes with the boards. But it's a brand-new little language, so the AI has never seen it and the parser has to guess what "Maya (annoyed)" means. Editor tweaks like "move Maya left 30px" also don't have a natural place to live.

Works well when

  • The written story matters as much as the pictures
  • Non-technical designers and PMs should edit it by hand
  • It's the closest match to how people naturally write storyboards

Watch out for

  • Custom text formats break often (Mermaid needed repair tools)
  • Visual tweaks end up in hidden comments or get lost
  • Hard to validate with specific, fixable errors

Storyboards as Code (TSX)

CoffeeOrder.storyboard.tsx 
export default () => (
  <Storyboard title="Late Latte">
    <Panel scene="coffee-shop/counter"
           shot="over-the-shoulder">
      <Maya pose="holding-phone"
            mood="annoyed">
        <Phone screen={orderStatus}>
          <Tap x={0.5} y={0.7} />
        </Phone>
      </Maya>
      <Thought>It said 4 minutes.</Thought>
    </Panel>
  </Storyboard>
)
AI writes→ type-checked→ editor⇄ rewrite source code?
Storyboards become React components, like how Remotion makes videos from code. It's endlessly powerful: loops, reusable "Maya's morning" snippets, custom props. TypeScript catches mistakes. But the editor would have to rewrite source code every time someone drags a bubble, which is fragile. It also turns a designer tool into a developer tool.

Works well when

  • Power users want logic and reuse (variants, persona swaps)
  • The audience is design engineers who live in React

Watch out for

  • Drag-and-drop edits writing back into code is a hard problem
  • Needs a build step, and running code means security concerns
  • Scares off the designers this is actually for

The case against my pick

Your whole thesis is getting teams to think like service designers, and the thing that does that is the story, not the file. A Markdown screenplay (C) is something a PM could read in a pull request, paste into a doc, or argue about in a crit. Nobody reads JSON for fun. If the editor is good enough, maybe nobody ever looks at the file, and then readability matters less than I'm assuming. If people do read the file, JSON is the worst of these four to read. The mitigation I'd build: A as the source of truth, plus a storyboard script command that prints a Markdown screenplay view (read-only) for humans.

This recommendation assumes

  • The coding agent writes almost all of the file. Designers mostly tweak visually, not by editing text
  • Editor changes must save back to the file so the AI can keep iterating (decision 8 depends on this)
  • The vocabulary (scenes, shots, poses, moods, devices) is finite and can be listed in a schema

What the research says

  • Across 21 models, JSON output was almost always syntactically valid, but 15–25 percent of the values inside were wrong. So the thing to build is semantic validation (valid moods, real scene IDs), not syntax checks. Structured Output Benchmark
  • Asking models for YAML output dropped syntax accuracy to about 0.6 on some models, while JSON in and JSON out performed best. Augment Code
  • Coding agents writing files don't get schema-guaranteed output, so a validate command with fix-it errors is the practical guardrail. claude-code #9058
  • Custom text formats break often enough that people build repair tools (e.g. for Mermaid diagrams). GenAIScript
  • Excalidraw's own answer to "AI is bad at our full file format" is a simplified skeleton format that expands into the full one. The authoring format and the render format are separate. Excalidraw docs
  • Full Excalidraw JSON produces noisy diffs because seeds, nonces and coordinates change on every edit. That's why pixel positions should be opt-in overrides. excalidraw #1639
  • YAML comments get lost on read-and-rewrite even with libraries built for round-trips. ruamel.yaml #426
  • Storyboarder (the open-source film tool) stores boards as JSON with a documented schema: a boards[] array with dialogue, action and notes. Storyboarder wiki
  • Slidev works well with agents because it's built on formats models already know (Markdown + YAML frontmatter) and ships an llms.txt. Slidev

Where experts disagree

The "docs as code" camp (Slidev, Fountain) says text humans can read wins adoption. The "visual editor" camp (tldraw, Excalidraw, Storyboarder) says the file is plumbing and should be structured data. What decides it: will your designers ever open the file? If the editor plus the AI covers everything, go structured. If the script itself is a deliverable, lean toward Markdown.
