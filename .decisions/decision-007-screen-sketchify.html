Uploaded Screens: Sketchify & Auto-Fit

This is your item 10. A designer drops their real, polished "Order status" screen into the storyboard. It has to stop looking polished so it matches the sketch, but still read as their product, and it should snap onto the phone, laptop, watch or dashboard automatically. Below, the same uploaded design goes through each approach. A and B are real browser filters running on the design right now, and C and D are illustrations of their typical output.

Option A
Chosen

Live Edge Filter

→
Small text turns into doubled outlines, and there's no teal
An SVG filter chain (grayscale, then edge detection, then a slight wobble) is applied live whenever the screen is drawn. Nothing is stored, and swapping the image is instant. Big shapes survive, but small UI text becomes doubled-outline mush, because edge detection draws both sides of every letter. It also ignores your "product = teal" rule, so the screen comes out ink-only.

Works well when

  • Zero processing step, fully live
  • Keeps the original file untouched

Watch out for

  • Text under about 14px becomes unreadable
  • Loses the teal product highlight
  • Heavy filters slow the editor, and resvg export may differ

Option B
My pickStrong pickChosen

Baked Teal Duotone

→
On upload, the screen is processed once: grayscale, posterized into four tones mapped to the teal product ramp, a light ink edge pass, and a slight wobble. The result is saved as a PNG next to the original. Text stays readable because it's filled rather than outlined, the screen instantly reads as "the product" in the teal-only system, and export is guaranteed to match what you saw. A slider controls how rough it looks.

Works well when

  • Follows the Marker Comp rule: the product is the only color
  • Readable copy, so reviewers can still read the UI
  • Baked PNG means fast editing and identical export

Watch out for

  • An extra file per screen in the project folder
  • Re-processing is needed if the roughness slider changes (about 100 ms)

Chosen

Trace to Vectors

→
Text becomes blobs, and the copy is lost
The screenshot is traced into vector shapes (vtracer running in the browser), then re-stroked with the fineliner so it looks genuinely hand-drawn. Boxes, buttons and maps look great, but text becomes squiggles. That's fine for a wireframe feel, bad when the copy matters ("ready in ~4 min" is the story here).

Works well when

  • The most convincingly hand-drawn result
  • Pure vectors, so it scales to any export size

Watch out for

  • All the UI copy is lost
  • Noisy on busy screens (maps, photos)
  • A heavier processing step (wasm tracer)

AI Redraw (Bring Your Own Key)

→
Copy changed: "Oak", "#241", "14 min", "I'm hear"
An image model redraws the screen as a hand-drawn sketch using the designer's own API key. The result can look beautiful, with hand-lettered text and clean lines. But diffusion models rewrite the copy: order numbers, times and labels quietly change, which is dangerous when the storyboard is about your real product. It also costs money, takes seconds, and needs a network connection.

Works well when

  • The most beautiful sketch output
  • Works on any image, even photos

Watch out for

  • Hallucinated copy means the storyboard misrepresents the product
  • Needs an API key, costs per image, needs a network
  • Different output every run
Respond with: "Option D"

Auto-fit, the same in every option

Every device in the library ships with its screen corners (the teal dots). Dropping a design onto a device fills that screen top-aligned, so tall scrolling screenshots show their first screen. Handles let you pan and scale inside the screen, or drag a corner. Angled devices (a tilted phone, a car dashboard) use a perspective warp computed from the four corners: a live CSS preview while editing, and a pre-warped image at export so the PNG matches exactly.

The case against my pick

Teal duotone means the screen is the most prominent thing in every panel it appears in. That's intended, but it can also pull the eye away from Maya's face, and her face carries the emotion you're trying to surface. It also still looks like a filtered screenshot rather than a drawing, which is lower-fi than the original but not truly hand-drawn like C. If early-stage teams would rather hide their unfinished UI copy, C's trace is more honest about how rough things are. Mitigation: a per-screen roughness slider, plus "wireframe mode" (C's look) as an optional alternative.

This recommendation assumes

  • The UI copy on the screen matters to the story ("ready in ~4 min" is the broken promise)
  • Uploads are mostly PNG/JPG exports from Figma, not live Figma links
  • The Marker Comp rule, that the product is the only color, should hold for uploaded screens too

What the research says

  • Edge-detection filters keep large type (16px and up) as outlined glyphs, but body text of 12px or less becomes doubled-edge mush because both sides of every stroke are drawn. feConvolveMatrix guide
  • Displacement "pencil" effects should stay at about 1–2px on screenshots, because higher values scramble text first. Here Dragons Abound
  • OpenCV.js is about 8–12 MB, which is far too heavy for one edge pass when a hand-written Sobel is a few KB. OpenCV Q&A
  • vtracer (wasm) traces flat UI well, but text turns into many tiny noisy blobs. vtracer
  • Diffusion line-art models still hallucinate or garble small text. RunComfy
  • SVG has no perspective transform. Compute a 4-corner homography (perspective-transform) for a CSS matrix3d preview, and pre-warp the raster (perspective.js / Homography.js) for export, because resvg ignores foreignObject and 3D transforms. perspective-transform Homography.js resvg foreignObject
  • Mockup tools (Rotato, Figma perspective plugins) store screen geometry per device template and fit automatically instead of asking users to place corners. Rotato Perspective Distort
